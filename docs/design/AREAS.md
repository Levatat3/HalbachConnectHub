# Areas: letting someone else have a page without handing over keys

An **area** is a lane on your site that one other person can send content into. They never log into anything of yours. Content travels one way, as data, into a review queue on your machine; you approve it; it joins your next Publish. A collaborator can run their own Halbach in **area mode** to edit their area comfortably and press "Send".

## 1. What an area is

```json
{
  "id": "workshop", "name": "Workshop", "slug": "workshop",
  "enabled": true, "trust": "review",
  "key": { "hash": "scrypt$...", "created": 1760000000, "last_used": null, "hint": "k7p2" },
  "limits": { "max_file_mb": 50, "max_bundle_mb": 80, "max_total_mb": 500, "max_files": 500,
              "extensions": ["md", "png", "jpg", "jpeg", "gif", "webp", "pdf", "txt", "zip"] },
  "blocks": ["text", "links", "cards", "gallery", "image", "files", "youtube", "twitch", "divider"],
  "allow_scripts": false,
  "notify": { "inbox": true }
}
```

- **Passphrase:** generated by Halbach (6 random words or 26 characters), shown **once**, stored only as a scrypt hash. The owner can regenerate or revoke at any time; revoking takes effect on the next request.
- **Scope:** the area owns exactly one address prefix (`/workshop/`). Its pages and files can only be written there; the builder enforces the prefix when it merges approved content, so a bundle cannot reach `/`, another area, `modules/`, `_halbach/` or any model page.
- **Allowed blocks:** a list, default safe set (above). Not included by default: `embed` (arbitrary URL), `live-view`, `module-*`, `dropbox`, `ruffle-game`, and any plugin block unless it is `isolated`.
- **Scripts off:** `allow_scripts` is `false`; there is no way for area content to ship JavaScript, HTML pages or SVG with script. A single owner switch can allow sandboxed HTML pages for a fully trusted area (they are served in a sandboxed frame without same-origin access).

## 2. The lifecycle of a submission

```
sender ──► drop endpoint ──► quarantine ──► validate ──► review queue ──► approve ──► approved version vN ──► next Publish
              (auth, size, rate)   (private folder)  (rules)      (owner sees diff)           (versioned)          (owner presses it)
                                                          └─ reject (with a note, kept 30 days)
```

1. **Receive.** Authenticated, size-capped, rate-limited (section 3). The raw upload is streamed to a temp file in the area's private quarantine folder.
2. **Validate.** The bundle is checked against every rule in section 4. Anything failing is rejected with a plain reason the sender can read.
3. **Queue.** A valid bundle becomes a *submission*: `{id, area, received, size, files, summary}`. The owner's window shows a banner and a review screen.
4. **Review** shows what changes: pages added/edited/removed, blocks used, files added/changed/removed (with sizes and hashes), and a **rendered preview** of the area's page(s) built into the local preview. The owner can approve, reject (with a note the sender can read), or ask for changes.
5. **Approve** creates `approved/v0007/` (a full snapshot, previous versions untouched). The area's pages now come from `v0007`. Rolling back is selecting an older version.
6. **Publish** is still the owner's button (or automatic at the highest trust level, below).

### Trust levels

| Level | A valid bundle... | Publish |
|---|---|---|
| `review` (default) | waits for approval | owner |
| `trusted` | is approved automatically (still validated, still versioned) | owner |
| `auto` | is approved and published automatically, debounced, at most one publish every N minutes | automatic |

Only the area's own prefix can ever change, at every level. `auto` is meant for a long-trusted collaborator and shows a standing banner in the window. A "pause" switch freezes an area instantly.

## 3. The drop endpoint (the only public door)

Served by the **live hub** through the tunnel; nothing else is added to the public surface. Routes:

| Route | Purpose |
|---|---|
| `POST /drop/<area>/bundle` | Upload a bundle (zip) in one request. |
| `POST /drop/<area>/file?name=...` | Upload one file (simple drop-box form) into the area's *pending files* submission. |
| `GET /drop/<area>/status` | The sender's recent submissions and their state (received, in review, approved, rejected + note). |
| `GET /drop/<area>/limits` | The area's limits, so a client can check before uploading. |

Hardening (each point is a test):

- **Auth:** `Authorization: Bearer <passphrase>`; constant-time comparison against the scrypt hash; no cookies, so no CSRF surface. Missing/invalid key returns the same 401 whether or not the area exists.
- **Rate limits:** per IP and per key, token bucket; after 10 failed attempts the key and IP are locked out for 15 minutes; global cap on concurrent uploads (default 2).
- **Size:** `Content-Length` is required and checked **before** reading; the body is streamed to a temp file with a hard cap while reading (a lying client is cut off); caps below Cloudflare's roughly 100 MB request limit (default 50 MB per file, 80 MB per bundle).
- **Method and type:** only `POST`/`GET`; bodies other than `application/zip` or `application/octet-stream` are refused; the declared type is never trusted.
- **CORS:** only the site's own origin(s) (for the upload form); the header-based key means a foreign page cannot upload without knowing the key anyway.
- **Disk safety:** quotas per area and globally; refuses when free disk is under a floor (default 2 GB); temp files cleaned on every path (success, failure, crash recovery on start).
- **No echo:** error bodies never include server paths or internals.
- **Audit log:** every attempt (time, IP hash, area, result, size) is logged; the window shows the last 100 per area.

## 4. Bundle format and the validation rules

A bundle is a zip:

```
area.json            required: { "format": 1, "title": "...", "description": "...", "blocks": [ {type, props}, ... ] }
files/...            referenced files (images, documents, markdown)
```

`area.json` describes the area's page(s): at minimum one page with ordered blocks, props following the same schemas as the main site (file references are relative to `files/`, and become `/<slug>/files/...`). Multiple pages are allowed under the prefix (`pages/<name>.json`).

Validation (all must pass; limits from the area):

- **Archive safety:** entry count ≤ `max_files`; names are normalised and must be relative, free of `..`, drive letters, absolute paths, NUL, backslashes and control characters; **no symlinks or special entries**; no duplicate names after case-folding (Windows); total uncompressed size ≤ `max_bundle_mb`; compression ratio per entry ≤ 20:1 and overall ≤ 20:1; nesting depth ≤ 8; entry names ≤ 120 characters. Extraction is manual and streaming, never `extractall`.
- **Files:** extension in the allow-list; **magic-number sniff agrees** with the extension for known types (PNG, JPEG, GIF, WebP, PDF, ZIP-in-ZIP is refused); executables, scripts, shortcuts, `.html`/`.htm`/`.js`/`.svg`/`.xml`/`.xhtml`/`.swf` refused unless the owner allowed scripts for the area; double extensions (`photo.png.exe`) and trailing dots/spaces refused; stored under generated names with the original kept as sanitised metadata.
- **Images:** dimensions read from the header and capped (default 8000 px) to defuse decompression bombs; EXIF GPS stripped when Pillow is available, otherwise a warning that location data may remain.
- **Markdown:** rendered by the safe renderer only; raw HTML shown as text; links scheme-checked.
- **Blocks:** type in the area's allow-list; props valid against the schema; URLs `https`/`mailto`/in-area relative only; `embed`-like blocks only to allow-listed hosts.
- **Model integrity:** the bundle cannot declare a slug, nav entry, theme, redirect, setting or page outside its prefix (any such key is ignored and reported); it cannot reference modules.
- **Quotas:** area total after approval ≤ `max_total_mb`.

## 5. The collaborator's side: area mode

`halbach --area` (or the same app with an area profile) is a restricted Halbach whose site model is **one page tree** and whose window shows only: **Page** (blocks editor, same forms), **Files** (the area's media), **Preview**, **Send**, **History**. No Publish, no tunnel, no settings, no other modules.

- **Connect:** `halbach area connect --url https://live.example.com --area workshop --key <passphrase>` stores the credentials (in the state folder with owner-only permissions, never in the repo).
- **Edit + preview:** builds locally with the owner's chosen theme (shipped to the collaborator as a plugin zip or the built-in theme named in the area), served at a local preview address.
- **Send:** zips the area (files + `area.json`), pre-checks it against the area's limits (fetched from `/limits`), uploads, then polls `/status` and shows "received / in review / approved / rejected: <note>".
- **CLI parity:** `halbach area send <folder>` does the same without the window, for scripts and chat tools; `halbach submit --remote` for single documents.
- The collaborator's own Halbach can also publish *their own* site elsewhere, since it is the same program; the area link is just one destination.

## 6. Notifications and collaboration

- The owner's window: dashboard banner, a badge on the Areas item, a toast while open.
- Optional outbound notification hook (a plugin): e.g. a chat message "New submission from Workshop (3 files)". Disabled by default; contains no file contents.
- **Review notes** travel back to the sender through `/status`.
- **Audit trail:** who (area), what (files, hashes), when, decision, who decided, kept for the life of the area.

## 7. Private areas

Unlisted is not private. For a truly private area the window shows a short recipe: create a Cloudflare Access application for `https://example.com/<slug>/*`, allow the collaborator's email(s) (free plan: up to 50 users, one-time PIN by email). The site cannot do this itself, and Halbach says so instead of faking a password box.

## 8. Threats specific to areas

| Threat | Mitigation |
|---|---|
| Stolen passphrase | Revoke/regenerate instantly; submissions still need review (or are limited to the area at `trusted`/`auto`); lockout and rate limits slow guessing; audit log shows use. |
| Malicious archive | Section 4 rules; manual streaming extraction; hard caps; quarantine folder outside any served path. |
| Script or HTML injection through content | Data-only pages; safe Markdown; scheme-checked links; no script/HTML/SVG allowed; strict CSP on the area's prefix (no script at all). |
| Defacement or phishing on the owner's domain | Review by default; area confined to its prefix; stricter CSP; the page shows an "area" label option; owner can freeze or roll back in one click. |
| Disk filling | Per-area and global quotas, disk floor, concurrency cap. |
| Probing for areas | Uniform 401; no listing endpoint; slugs are not secrets but keys are. |
| Large-file bypass of the proxy limit | Caps below the proxy limit; chunking is a later item, not a loophole. |
| Replay of a captured request | TLS only (the tunnel is HTTPS); bundles are idempotent (identical content hash is recognised and ignored). |
